# 設計上の判断

DDD の一般的なやり方から、このアプリの事情に合わせて意図的に外したり、選んだりしたことの記録。
前提が変わったら見直すために、「見直す条件」も書いておく。

## D1. 献立の変更で動く食事は、1 つのトランザクションで保存する

**決めたこと**
献立を変える操作では、変えた食事と、残り物を外したほかの日の食事を、
`save_meals`（Postgres 関数）で 1 つのトランザクションとしてまとめて保存する（`src/application/use-cases.ts` の `changeMeals`）。
レシピを削除したときは、レシピの削除と、それを使った品を外した食事も同じトランザクションに入れる。

**一般的なやり方との違い**
DDD では「1 回の保存で変えるのは集約 1 つ。ほかの集約にはドメインイベントで後から反映する（結果整合性）」が基本。
ここでは複数の食事（集約）を同時に変えている。

**理由**
- 使うのは家族 2 人で、同時に大量の更新が起きない。集約をまたいで同時に書き換えても、ロックの取り合いがほぼない
- すべて同じデータベースにあるので、まとめて保存するのが一番簡単で確実
- 結果整合性にすると、「元の品は外れたのに、翌日の残り物だけ残っている」状態が一時的に起きる
- 結果整合性に必要な仕組み（イベントの保存・再送・重複の扱い）を作って保守するほどの規模ではない

**経緯**
以前は買い物リストも献立に合わせて自動で増減していたので、買い物リストも同じトランザクションに入れていた。
買い物メモにしてからは献立の変更でメモは変わらないので、メモは別に保存する（[D6](#d6-買い物メモは版の番号で書き換えのぶつかりを見つけ行単位でまとめる)）。保存の関数も `save_meals_and_shopping` から `save_meals` に改めた（0009）。

**見直す条件**
- 利用者が増えて、同じ行の取り合いでエラーや待ちが目立つようになったとき

## D2. 画面に出すための読み込みは、ドメイン層を通さない

**決めたこと**
献立画面（`src/lib/meals.ts`）や買い物リストの再読み込みは、Supabase から表示に必要な形で直接読む。
書き込みは必ずユースケースとドメイン層を通す。

**理由**
- 表示には、レシピの画像や名前など集約が持たない情報が必要で、集約を組み立ててから表示用に変換するのは手間に見合わない
- 読み込みはルールを破らない。ルールが必要な判定（残り物にできるか等）は、ドメイン層の関数（`whyNotLeftover` など）を呼んで同じ結果にする

**守ること**
読み込み側にルールを書き写さない。条件が必要ならドメイン層に関数を作って呼ぶ。

## D3. ドメインイベントは集約から取り出して、その場でドメインサービスに渡す

**決めたこと**
食事の集約は起きたことを溜め、ユースケースが `pullEvents()` で取り出して、同じ処理の中でドメインサービス（`removeLeftoversOfRemovedDishes`）に渡す。
「品が献立から外れた」を受けて、その品の残り物をほかの日の食事から外す（M7）。
イベントを保存したり、別の処理で受け取ったりする仕組み（イベントバス）は作らない。

**理由**
D1 で同じトランザクションにまとめているので、イベントを後から届ける必要がない。

**経緯**
以前はイベントを買い物リストのポリシー（`applyMenuEvents`）にも渡し、どの出来事に反応するかを `switch` の網羅性チェックで確かめていた。
買い物メモにしてからは、献立の出来事に反応するのは残り物の片付けだけになったので、ポリシーは消した。

**見直す条件**
D1 を見直して結果整合性にするとき。

## D4. ルールのテストはメモリ上の保存先で行い、問い合わせ文は本番で別に確かめる

**決めたこと**
ドメイン層とユースケースのテストは、メモリ上の保存先（`InMemoryStore`）で動かす。
Supabase への問い合わせ文（`select` の書き方）を変えたときは、本番の Supabase にログインせずに問い合わせを送り、解析が通るかを確かめてから本番に出す（RLS で守られているので中身は読めない）。

**理由**
テストを速く（全体で 0.1 秒ほど）保ち、ルールの確認をいつでもできるようにするため。
一方で、メモリ上の保存先では問い合わせ文の誤りに気づけず、実際に本番で献立が読めなくなったことがある（`!left` を左結合と読まれた件）。

**見直す条件**
問い合わせ文の誤りがまた本番で起きたとき。ローカルで Supabase を動かすテストを足すことを検討する。

## D5. 写真は「URL を知っていれば見られる」保存場所に置く

**決めたこと**
写真から取り込んだ画像は、Supabase Storage の公開バケット `recipe-images` に、推測できないランダムな名前（UUID）で置く。
アップロードと削除は家族だけ（RLS）。保存場所の一覧は外から見られない。

**一般的なやり方との違い**
家族だけのデータは非公開にするのが基本で、レシピや献立は RLS で家族以外には読めないようにしている。画像だけは URL を知っていれば誰でも見られる。

**理由**
- 非公開にすると、一覧・献立・詳細・献立のシートなど写真を出すすべての画面で、表示のたびに期限付きの URL を発行する仕組みが要る
- 置くのは料理本・雑誌のページやスクリーンショットで、知られて困る内容ではない
- URL は推測できず、一覧も外から取れないので、URL を共有しない限り見られない

**見直す条件**
家族の写真など、知られて困る画像を置くようになったとき。期限付き URL（signed URL）に切り替える。

**残っていること**
取り込みを途中でやめたときやレシピを削除したときの画像は、保存場所に残る（容量が問題になったら片付ける仕組みを作る）。

## D6. 買い物メモは版の番号で書き換えのぶつかりを見つけ、行単位でまとめる

**決めたこと**
買い物メモは 1 つの文章として保存し、保存するたびに版の番号（`version`）を 1 つ増やす。
保存するときは、手元で書き始めたときの版を添え、保存されている版と同じときだけ保存する（`save_shopping_memo`。楽観的ロック）。
版が違えば、相手が先に保存している。そのときは最新のメモを読み直し、「書き始めたときの文章」から手元で変えたこと（足した行・消した行・チェックの切り替え）を最新のメモに当てはめてから保存し直す（`mergeMemoText`。3 回まで）。
画面でも、保存している間に書き足した分や、Realtime で届いた相手の変更を同じやり方でまとめる。

**ほかのやり方を選ばなかった理由**
- **後から保存した方で上書きする**: 夫が献立の材料を反映している間に妻が書いた行が消える。買い忘れにつながるので避けた
- **行ごとに別の行（レコード）として保存する**: 以前の買い物リストはこの形だったが、メモ帳のように文章を自由に直す（行をまたいで消す・貼り付ける・並べ替える）と、行の対応を取るのが画面側で難しくなる
- **共同編集の仕組み（CRDT など）を入れる**: 2 人で使うメモには大げさ。同じ行を同時に直すことはほとんどない

**分かっている弱点**
- 2 人が同じ行を同時に別の文章に直すと、両方の行が残る（どちらかを消すかは家族が決める）
- 同じ文章の行が何行もあると、どの行を消したかの対応がずれることがある

**見直す条件**
同じ行の書き換えがぶつかって困ることが続いたとき。
