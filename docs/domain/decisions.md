# 設計上の判断

DDD の一般的なやり方から、このアプリの事情に合わせて意図的に外したり、選んだりしたことの記録。
前提が変わったら見直すために、「見直す条件」も書いておく。

## D1. 献立と買い物リストを 1 つのトランザクションで保存する

**決めたこと**
献立を変える操作では、変えた食事・残り物を外したほかの日の食事・買い物リストを、
`save_meals_and_shopping`（Postgres 関数）で 1 つのトランザクションとしてまとめて保存する（`src/application/use-cases.ts` の `changeMeals`）。

**一般的なやり方との違い**
DDD では「1 回の保存で変えるのは集約 1 つ。ほかの集約にはドメインイベントで後から反映する（結果整合性）」が基本。
ここでは食事（集約）と買い物リスト（集約）を同時に変えている。

**理由**
- 使うのは家族 2 人で、同時に大量の更新が起きない。集約をまたいで同時に書き換えても、ロックの取り合いがほぼない
- すべて同じデータベースにあるので、まとめて保存するのが一番簡単で確実
- 結果整合性にすると、「献立には入ったのに買い物リストに材料がない」状態が一時的に起きる。買い出し中に見る画面でそれが起きるのは困る
- 結果整合性に必要な仕組み（イベントの保存・再送・重複の扱い）を作って保守するほどの規模ではない

**見直す条件**
- 利用者が増えて、同じ行の取り合いでエラーや待ちが目立つようになったとき
- 買い物リストを別のサービス（外部のアプリなど）に置くことになったとき

## D2. 画面に出すための読み込みは、ドメイン層を通さない

**決めたこと**
献立画面（`src/lib/meals.ts`）や買い物リストの再読み込みは、Supabase から表示に必要な形で直接読む。
書き込みは必ずユースケースとドメイン層を通す。

**理由**
- 表示には、レシピの画像や名前など集約が持たない情報が必要で、集約を組み立ててから表示用に変換するのは手間に見合わない
- 読み込みはルールを破らない。ルールが必要な判定（残り物にできるか等）は、ドメイン層の関数（`whyNotLeftover` など）を呼んで同じ結果にする

**守ること**
読み込み側にルールを書き写さない。条件が必要ならドメイン層に関数を作って呼ぶ。

## D3. ドメインイベントは集約から取り出して、その場でポリシーに渡す

**決めたこと**
集約は起きたことを溜め、ユースケースが `pullEvents()` で取り出して、同じ処理の中でポリシー（`applyMenuEvents`）に渡す。
イベントを保存したり、別の処理で受け取ったりする仕組み（イベントバス）は作らない。

**理由**
D1 で同じトランザクションにまとめているので、イベントを後から届ける必要がない。
どの出来事に反応するかは、ポリシーの `switch` の網羅性チェックでコンパイラに確かめさせている。

**見直す条件**
D1 を見直して結果整合性にするとき。

## D4. ルールのテストはメモリ上の保存先で行い、問い合わせ文は本番で別に確かめる

**決めたこと**
ドメイン層とユースケースのテストは、メモリ上の保存先（`InMemoryStore`）で動かす。
Supabase への問い合わせ文（`select` の書き方）を変えたときは、本番の Supabase にログインせずに問い合わせを送り、解析が通るかを確かめてから本番に出す（RLS で守られているので中身は読めない）。

**理由**
テストを速く（全体で 0.1 秒ほど）保ち、ルールの確認をいつでもできるようにするため。
一方で、メモリ上の保存先では問い合わせ文の誤りに気づけず、実際に本番で献立が読めなくなったことがある（`!left` を左結合と読まれた件）。

**見直す条件**
問い合わせ文の誤りがまた本番で起きたとき。ローカルで Supabase を動かすテストを足すことを検討する。

## D5. 写真は「URL を知っていれば見られる」保存場所に置く

**決めたこと**
写真から取り込んだ画像は、Supabase Storage の公開バケット `recipe-images` に、推測できないランダムな名前（UUID）で置く。
アップロードと削除は家族だけ（RLS）。保存場所の一覧は外から見られない。

**一般的なやり方との違い**
家族だけのデータは非公開にするのが基本で、レシピや献立は RLS で家族以外には読めないようにしている。画像だけは URL を知っていれば誰でも見られる。

**理由**
- 非公開にすると、一覧・献立・詳細・献立のシートなど写真を出すすべての画面で、表示のたびに期限付きの URL を発行する仕組みが要る
- 置くのは料理本・雑誌のページやスクリーンショットで、知られて困る内容ではない
- URL は推測できず、一覧も外から取れないので、URL を共有しない限り見られない

**見直す条件**
家族の写真など、知られて困る画像を置くようになったとき。期限付き URL（signed URL）に切り替える。

**残っていること**
取り込みを途中でやめたときやレシピを削除したときの画像は、保存場所に残る（容量が問題になったら片付ける仕組みを作る）。
