# このコードで DDD を学ぶ

開発者の視点で、このリポジトリを教材にドメイン駆動設計（DDD）を学ぶための道しるべ。

このリポジトリは、作る過程（聞き取り → 言葉 → モデル → コード → 見直し）がすべてドキュメントと git の履歴に残っている。教科書の例題と違って、「なぜこうなったか」「どこで間違えたか」まで追えるのが教材としての強み。

## 1. DDD は 2 つの層でできている

| 層 | 問い | このリポジトリでの例 |
|---|---|---|
| **戦略的設計**（言葉と境界） | 何を作るべきか。どこで言葉の意味が変わるか | [用語集](glossary.md)、[コンテキストマップ](context-map.md)、「材料」と「買う物」の区別 |
| **戦術的設計**（コードの型） | ルールをどうコードに閉じ込めるか | 値オブジェクト、集約、ドメインイベント、リポジトリ（Store） |

開発者はコードの型（戦術）から入りがちだが、このプロジェクトで一番効いたのは戦略のほうだった。「豚ばら肉と豚ロース肉は別の物」という言葉の定義から、合算の不具合が見つかった。**コードの型は、言葉とルールを守るための手段**と捉える。

## 3. 読むときに自分に問う質問

パターンの名前を覚えるより、**「なぜそこに置いたか」を自分で説明できるか**を確かめる。

| パターン | 自分に問う質問 | このコードでの答え |
|---|---|---|
| 値オブジェクト | 「同じかどうか」の判断に、ドメインのルールがあるか | 食材は全角・半角の違いを無視するが、部位は区別する（`Food.equals`）。ただの `string` では表せない |
| エンティティか値か | 後から ID で追いかける必要があるか | 品（`Dish`）は買い物リストの「出どころ」から ID で参照されるのでエンティティ。残り物（`Leftover`）は元の品を指すだけなので値 |
| 集約 | 一緒に変わらないと矛盾するものは何か | 「外食」と「品」は同時に整合していないといけない（外食なのに品がある、は矛盾）。だから同じ食事（`Meal`）の集約に入れる |
| ドメインサービス | そのルールは、1 つの集約の中だけで判断できるか | M10（残り物にしている品は 2 人分以下にできない）は、ほかの日の食事を見ないと判断できないので、食事のクラスには置けない |
| ドメインイベント | 過去形で言えるか。誰がそれに関心を持つか | 「品が献立から外れた」（`DishRemoved`）に、買い出しのコンテキストが関心を持つ |
| ポリシー | 「〜したら、〜する」と言えるか | 品が外れたら、まだ買っていない材料を消す。どの出来事に反応するかは `switch` の網羅性チェックでコンパイラに確かめさせている |
| アプリケーション層 | ここに if 文でルールの判断が入っていないか | 見直しの前は M10 がここにあった（コミット `a049bec` で移した） |
| 腐敗防止層 | 外部の言葉が、中まで入り込んでいないか | schema.org の `Recipe` や YouTube の形式は `src/lib/import/` の中だけで扱い、外にはレシピの下書きとして渡す |
| リポジトリ | ドメインが保存先の都合を知らずに済んでいるか | ドメイン層は Supabase を import しない。保存先は `Store` インターフェースで、テストではメモリ上の実装に差し替える |

## 4. このコードで練習する課題

易しい順。**どれも、まずドメイン層のテストを 1 つ書いてから**始める。

1. **常備品を買い物リストに出さないようにするとしたら？**
   「常備品」はどの概念に属するか（食材の性質か、家族ごとの設定か、買い物リストの表示の問題か）を考える。今のモデルで「区別しない」と決めた理由（[用語集](glossary.md)）を考え直す練習になる。

2. **品を別の日に移せるようにする（`DishMoved` を足す）**
   足した瞬間に、ポリシーの網羅性チェックでコンパイルが止まる。そのうえで次を決めることになる。
   - 買い物リストの「使う日」はどう変わるか
   - 移した結果、残り物が元の品より前の日になったらどうするか（M6）
   - これはドメインエキスパートに聞くべき質問か

   イベント・ポリシー・不変条件をまとめて考えられる。

3. **買い物リストを売り場ごと（野菜・肉・調味料）に分ける**
   「売り場」は食材の性質か、店ごとに違うものか。どのコンテキストの言葉かを考える練習になる。

4. **D1 をやめて、結果整合性にしてみる（上級）**
   献立と買い物リストを別々に保存するには何が必要になるか（イベントの保存・再送・二重に届いたときの扱い）。考えると「なぜ今はまとめて保存しているのか」が実感できる。

## 5. このリポジトリで実際に起きた失敗

教科書では見えにくい、実際の失敗の記録。コミットを `git show <コミット>` で追える。

| 起きたこと | 教訓 | 追える場所 |
|---|---|---|
| レシピの保存がドメインを通らず、ルールが画面とドメインの 2 か所にあった | ルールが集約の外に漏れると、データだけでルールを持たない「貧血ドメインモデル」になる | `97f7a6a` |
| 残り物にできるかの判定が、読み込み側にもコピーされていた | 読み込み側にルールを書き写さない。必要ならドメインの関数を呼ぶ | `cf9c8c2`、[D2](decisions.md) |
| `Recipe` という名前が、DB の行とドメインの集約の 2 つの意味で使われていた | コードの名前もユビキタス言語の一部 | `f3e8a36` |
| テストは全部通ったのに、本番で献立が読めなくなった | ドメインのテストは、インフラ（問い合わせ文）の正しさを保証しない | `f4817b4`、[D4](decisions.md) |
| ドキュメントとコードが 15 か所ずれていた | 言葉は放っておくと腐る。ルールを変えるときは、コード・テスト・ドキュメントを同時に直す | `b496e70` |
| ポリシーが反応しない出来事を、黙って無視していた | 「反応しない」も決定として明示し、コンパイラに守らせる | `23291e2` |

## 6. 本で補う

| 本 | 向いていること |
|---|---|
| 『ドメイン駆動設計をはじめよう』（Vlad Khononov） | 戦略的設計から入れる。最初の 1 冊に |
| 『ドメイン駆動設計入門』（成瀬允宣） | 値オブジェクトや集約などの型を、コード例で丁寧に |
| 『実践ドメイン駆動設計』（Vaughn Vernon） | 集約の設計。[D1](decisions.md) で外した「1 回の保存で変えるのは集約 1 つ」の原則が詳しい |
| 『エリック・エヴァンスのドメイン駆動設計』 | 原典。上の本の後に |

## 7. 進め方

1. 「読む順番」に沿って読み、「自分に問う質問」に答えられるか確かめる
2. 練習課題を 1 つ選び、ドメイン層のテストから書いて実装する
3. 迷ったら、それが「ドメインエキスパートに聞くべきこと」か「開発者が決めてよいこと」かを考える。聞くべきことなら、決めた内容を [event-storming.md](event-storming.md) と [domain-model.md](domain-model.md) に残す
